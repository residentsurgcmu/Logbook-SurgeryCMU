# Activity calendar v1 — review handoff

Base: a8bfeddbdbf9ecf126719123c2bfaf7944279973 (PR32).
Scope: independent monthly agenda and next-90-days My Space card. No automatic e-mail, notification job, resit rules, attendance changes, or score publication. No production changes in this task.

## User workflow

- All roles have a new “ปฏิทินกิจกรรม” menu. Existing external duty/OR embeds remain separate.
- Admin creates a client-identified draft, checks details/recipient list, then chooses published and confirms. Editing and cancellation preserve history; there is no destructive delete endpoint.
- Audience is 1–200 active Residents: all, selected PGYs 1–5, or selected accounts. Membership and PGY are captured when created or audience selection changes. A details/status edit preserves that snapshot even after PGY/account changes. To replace an existing all-Resident snapshot, explicitly choose individual recipients rather than expecting it to refresh automatically.
- Active Residents see only their published/cancelled events. Active Staff see all published/cancelled events, without recipient lists. Admin list mode is separately checked. Disabled accounts cannot read even using an existing JWT.
- Admin can optionally link an RC04 managed exam. Publishing a schedule does not publish the exam, modify its metadata/roster, or change scores. A non-Admin receives an exam ID only once that exam has a published pointer. The button opens the existing result page with its existing authorization; it does not auto-reveal personal scores. Legacy MCQ linking is deferred.
- My Space overview lists at most three upcoming noncancelled items, using existing score-privacy defaults unchanged.
- Times use Asia/Bangkok; inputs are Gregorian dates displayed by the device, agenda dates use Thai locale. Month ranges are half-open, overlap-aware, deterministic by starts_at + id.

## API and storage

- `save_resident_calendar_event(uuid,integer,jsonb)`: active Admin required; UUID generated by client, expected version 0 creates. Advisory identity lock then row lock; expected version prevents stale changes. Immediate replay of the same payload at expected+1 returns current identity/version; same current payload is no-op. It is not a durable cross-version receipt protocol. Conflicting or ambiguous results require reload/readback before a new event.
- Required payload keys: title, kind, starts_at, ends_at, location, description, status, audience_mode, pgys, user_ids, exam_id. No extra keys. Timestamps finite; end after start, max 14 days. Payload/audience types and duplicates checked; selected accounts must all be active Residents.
- `list_resident_calendar_events(timestamptz,timestamptz,boolean=false)`: active account required on every call; Admin mode separately guarded. Range at most 93 days. Max 500 full events; 501 fails instead of returning a partial list. Admin gets audience configuration and captured recipients; other actors get neither.
- Three additive RPC-only tables: events, participants, audit. RLS enabled without direct policies; all public/anon/authenticated/service_role table/sequence privileges revoked explicitly. Only the two guarded public functions are granted to authenticated; private helper revoked. Owner/SQL access is trusted administration, not a browser authorization path.
- Audit records actor/version/time/submitted event and selected identities on each real change. Replay/no-op produces no new audit. No direct browser audit reader/writer.
- Component lifecycle aborts list reads and discards old responses. Calendar and upcoming cards are keyed by user. Save callbacks after unmount cannot update the new page. Refresh/logout does not restore an unfinished editor; notice instructs readback first.
