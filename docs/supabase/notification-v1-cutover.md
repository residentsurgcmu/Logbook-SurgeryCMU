# Notification preferences: exact cutover and rollback (v3.1 + hosted check-in fix)

This runbook is for the assessment mail worker only. It keeps web notifications and the invite/password mail flows available. Use only on an authorized target and with an approved package. First rehearse on non-production with synthetic users, a controlled mail sink, and access to the Edge invocation logs. Do not use this as a record of a completed rollout.

## Stop old send admission before applying the database changes

1. Record the existing notifier deployment ID, cron job ID and current UTC time; verify there is exactly one assessment-email cron job and verify the target project. Disable that job using `select cron.alter_job(<verified job id>, active := false);` and read back false. This step alone does not stop browser-triggered mail.
2. Deploy the exact candidate `resident-assessment-notifier` bundle **before** applying these migrations. Its browser and cron routes both check in using the new RPC before reserving or reaching transport. On the Base database that RPC is absent, so the exact candidate fails closed: a valid cron invocation and a signed-in synthetic Resident invoking an owned request must return HTTP 500 with `workerVersion: rc-notif-v1-impl-v3` and the check-in unavailable error. Confirm the check-in RPC is absent on Base with a read-only catalog query. Confirm the actual deployed ID in the platform and both responses on the target URL. Never log the secret, JWT, or message body. Any unexpected response or ambiguity means stop with cron disabled.
3. From confirmed candidate rollout and both fail-closed probes, wait at least 10 minutes, and confirm this exceeds the target's current hard worker wall-clock limit. Cross-check invocation logs for the deployment transition and any later activity from the old revision; restart the wait after the last observed old invocation, and do not proceed if you cannot establish rollout and a bounded drain on the target. A browser response/timeout, the cron flag or a delivery row's age alone does not prove legacy termination. The old worker has no way to be fenced after it has already obtained permission: an accepted message may still be delivered by its provider.
4. With cron still off, apply `20261118090000_notification_preferences_v1.sql`, `20261118090100_schedule_notification_web_retry.sql`, and `20261118090200_notification_worker_checkin_where.sql` in that order, then reload the schema cache. The third migration scopes worker check-in to the one control row; hosted PostgREST rejected the original unconditional UPDATE. Verify all 16 postdeploy rows true and exactly one inactive email cron job. The switch starts paused; the legacy claim raises, so even a misrouted old revision cannot obtain another claim. Re-run both authenticated probes: both must return HTTP 200, `paused: true`, and `workerVersion: rc-notif-v1-impl-v3`; neither may attempt transport. Check deployed ID/logs again. Do not merge the frontend until these checks pass.
5. After this pause has lasted at least 10 minutes, inspect outstanding reservations and attempts. Run `notif_v1_mail_drain_abandoned.sql` only after the runtime drain evidence above; unresolved legacy sends and expired authorized attempts are classified uncertain and never retried. v3 reservations that had not reached authorization are made eligible for retry. Require 0 open reservations and 0 open attempts; stop if either count is nonzero. Classification is not a substitute for the runtime evidence.
6. While paused, perform fresh probes on both routes again, matching the deployed candidate. Within five minutes run `notif_v1_mail_worker_resume.sql` and verify true/false. This script serializes with both types of admission and checks a fresh candidate check-in after the drain window. A stored check-in by itself does not establish what version serves the two live routes. Verify the first legitimate cron round, mail sink, and a later round (including a synthetic opted-out item and a subsequent eligible item).

Supabase hosted [runtime limits](https://supabase.com/docs/guides/functions/limits) and [invocation logs](https://supabase.com/docs/guides/functions/logging) are the sources for the wall-clock limit and cross-check. Verify the actual target at rehearsal; do not apply the wait rule to an unbounded self-hosted worker.

The staging Mailtrap checks used a temporary, staging-only STARTTLS probe and send path on port 2525. That code is not in this candidate. Keep the existing production mail provider and transport configuration; verify the provider selection without printing secrets, and validate delivery on an explicitly approved test recipient. The Mailtrap result does not prove production SMTP or a scheduled email wake-up.

## Pause / roll back after cutover

Run the transactional `notif_v1_mail_worker_pause.sql` to close admission at the shared control row and disable email cron. Verify false/true. An authorization completed before pause may still send; capture old in-flight counts, runtime evidence and final counts before classifying any abandoned rows. Keep all DB state, including suppressions, preferences, queues and legacy-claim retirement. The frontend can be reverted with mail paused; never restore the old claim. Resume only against a verified bundle that honors the new reserve/authorize path, following the same drain and live probe checks. Rehearse these steps with harmless fixtures before production approval.
